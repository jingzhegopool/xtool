## 1. 背景与目标

### 1.1 现状问题

xtool/pool v0.3.x 的任务池缺少对**单个任务**的生命周期控制:

| 能力 | 现状 | 说明 |
|---|---|---|
| 移除 | ✅ `DeleteTask(id)` | 任何状态直接删 |
| 终止 | 🟡 `Cancel(id)` | **只对排队中任务生效**,运行中任务无法取消 |
| 停止(暂停) | ❌ 无 | `Pause()`/`Resume()` 是空壳,且是池级(全局)语义 |
| 启动/继续 | ❌ 无 | 任务一旦离开 pending,只能重新 Submit,无法手动激活 |

闲鱼本地版(pooladapter)已接入 xtool/pool,但前端对"运行中任务"没有任何控制手段——批量核价、批量发布这类长任务一旦跑起来,只能等它结束。

### 1.2 目标

为**单个任务**提供四个操作,全部落库、全部可观测。每个任务内部包含多个小任务(业务 handler 循环处理),操作语义如下(用户需求):

- **启动 Start**:延迟执行的任务用户改变主意想立即执行 → 立即入队执行;也支持重新激活 paused / failed / cancelled 任务
- **停止 StopTask**:正在执行的小任务**继续执行完成**,但**不再启动新的小任务**;已进入执行的小任务执行完即停止(排空语义),保留进度可恢复
- **终止 Terminate**:发出停止信号,任务池执行完已经进入执行的小任务后才终止(排空语义),终态 cancelled 不可恢复
- **移除 Remove**:**只能等任务停止之后才能移除**(运行中直接拒绝)

### 1.3 非目标

- 不做池级(全局)暂停/恢复(保留 `Pause()`/`Resume()` 空壳,文档注明)
- 不做"强杀"运行中 goroutine(Go 语言限制,见 §4)
- 不做任务的资源限制(CPU/内存/带宽)——那是另一个话题

## 2. 核心设计原则

### 2.1 协作式取消(Cooperative Cancellation)

**Go 没有 API 能强制杀死一个 goroutine**,这是语言层面的硬约束。因此"停止/终止运行中任务"只能走协作式:

```
框架发信号(取消 ctx) → handler 监听 ctx.Done() → handler 主动返回 → 框架收尾写终态
```

信号机制用 Go 标准库 `context`。现有 `task.Timeout` 已经用了 `context.WithTimeout`,本次改造把**手动取消**和**超时**统一到同一套机制上。

### 2.2 状态机(核心)

```
                     ┌────────────────────────────────────────┐
                     ▼                                        │
pending ──► running ──► paused ──(Start/Continue)─────────────┘
   │           │                       │
   │           │                       └──(Terminate)──► cancelled
   │           └──(Terminate)──────────► cancelled
   └──(Terminate)─────────────────────► cancelled
                (任一非终态)

failed ──(Start)──► pending ──► running        ← 重新运行,重试计数清零
cancelled ─(Start)─► pending ──► running       ← 重新激活
completed ────────────────────────────────────  ← 不可变,不可启动
```

| 状态 | 值 | 含义 | 可操作 |
|---|---|---|---|
| `StatusPending` | 0 | 等待执行 | Terminate, Remove |
| `StatusDelayed` | 1 | 等待调度时间 | Terminate, Remove |
| `StatusRunning` | 2 | 正在执行 | **Stop**, Terminate, Remove |
| `StatusCompleted` | 3 | 成功 | Remove |
| `StatusFailed` | 4 | 失败(无重试机会) | **Start**, Remove |
| `StatusCancelled` | 5 | 已取消/终止 | **Start**, Remove |
| `StatusRetrying` | 6 | 失败待重试 | (保留,不直接暴露) |
| `StatusPaused` | 7 | **手动暂停(新增)** | **Start/Continue**, Terminate, Remove |

> `StatusPaused = 7` 是整数常量,SQLite/MySQL 的 `status TINYINT` 列**无需迁移**,旧数据不冲突。

### 2.3 操作语义矩阵

| 操作 | pending | delayed | running | paused | failed | cancelled | completed |
|---|---|---|---|---|---|---|---|
| Start | ✗ | ✅ 立即执行 | ✗ | ✅ 继续 | ✅ 重跑 | ✅ 重跑 | ✗ |
| StopTask | ✗ | ✗ | ✅ 排空暂停 | ✗ | ✗ | ✗ | ✗ |
| Terminate | ✅ | ✅ | ✅ 排空终止 | ✅ 直接置 | ✅ 直接置 | ✗(已终态) | ✗ |
| Remove | ✅ | ✅ | ✗ 拒绝 | ✅ | ✅ | ✅ | ✅ |

**关键语义决策**:
1. **Start 支持 delayed(用户场景)**:延迟任务改变主意 → 清 ScheduledAt → pending → 立即执行。
2. **Start 对 failed/cancelled 是"重新运行"**:重试计数清零,视为全新一次。否则一个 MaxRetries 耗尽的 failed 任务,Start 后立刻再次失败。
3. **Start 对 paused 是"继续"**:保留进度、metadata、重试计数,`StartedAt`/`DoneAt`/`Error` 清空。
4. **StopTask 只对 running 生效**:对已终态任务返回 `ErrTaskNotRunning`(幂等语义由调用方处理)。
5. **Remove 只对非 running 生效**:运行中任务返回 `ErrTaskNotRemovable`,必须先 StopTask/Terminate 等状态变为 paused/cancelled 再移除(用户明确要求)。
6. **Terminate 对 paused/failed 的"直接置"是幂等补刀**:把已是终态的任务再标一次 cancelled,便于前端统一"终止按钮永远可用"。
7. **停止/终止是排空语义**:正在执行的小任务跑完,不再启动新小任务。依赖 handler 在"小任务之间"检查 ctx.Done()(见 §8)。

## 3. API 设计

### 3.1 新增方法(全部在 `TaskPool` 上)

```go
// Start 重新激活一个非活动任务(重新入队执行)。
//   delayed → 立即执行（清除调度时间，改变主意场景）
//   paused  → 继续执行(保留进度、metadata、重试计数)
//   failed / cancelled → 重新运行(重试计数清零)
// 其他状态返回 ErrTaskNotStartable。
func (p *TaskPool) Start(id string) error

// Continue 继续执行一个已停止的任务,等价于 Start,语义更明确。
func (p *TaskPool) Continue(id string) error

// StopTask 停止一个运行中的任务(排空语义)：
// 已经进入执行的小任务继续执行完成，但不再启动新的小任务；
// 保留进度和 metadata，可通过 Continue 恢复。
// 非运行中任务返回 ErrTaskNotRunning。
func (p *TaskPool) StopTask(id string) error

// Terminate 终止一个任务,终态为 cancelled（排空语义，同 StopTask 但不可恢复）。
//   running → 发送取消信号,handler 退出后写入 cancelled
//   pending / delayed → 直接标记 cancelled
//   paused / failed → 直接标记 cancelled(补刀)
//   cancelled / completed → 返回错误(幂等判断由调用方做)
func (p *TaskPool) Terminate(id string) error

// Remove 移除任务(从存储彻底删除,不可恢复)。
// 仅限非运行中任务：running 返回 ErrTaskNotRemovable，
// 必须先 StopTask（等变 paused）或 Terminate（等变 cancelled）后再移除。
func (p *TaskPool) Remove(id string) error
```

### 3.2 兼容性

- `Cancel(id) bool` 保留,内部改为 `return p.Terminate(id) == nil`(行为升级:运行中任务也能取消了)
- `DeleteTask(id) error` 保留,内部改为 `return p.Remove(id)`(行为升级:运行中任务会拒绝删除)
- **接口 `Backend` 零改动**,`pooladapter`(闲鱼适配层)无需编译修改
- 新增错误: `ErrTaskNotRunning`、`ErrTaskNotStartable`、`ErrTaskNotRemovable`
- 命名说明:池级 `Stop()`(关闭整个任务池)是既有公开 API 不能改,单任务停止命名为 `StopTask(id)` 避免重名

### 3.3 新增状态

```go
StatusPaused TaskStatus = 7 // 手动暂停,可恢复
```

`String()` 增加 `"paused"` 分支。

## 4. 技术实现

### 4.1 数据结构(engine.go)

```go
type TaskPool struct {
    // ...原有字段...

    // 运行中任务的取消注册表 + 干预信号
    controlMu      sync.Mutex
    runningCancels map[string]context.CancelFunc // id => cancel(),仅 running 任务存在
    stopSignals    map[string]TaskStatus         // id => 期望终态(StatusPaused / StatusCancelled)
}
```

- `runningCancels`:任务开始执行时注册 cancel,结束时(无论何种终态)注销。Stop/Terminate 从这里查表。
- `stopSignals`:记录"外部要求这个任务最终变成什么状态"。handler 退出后,收尾逻辑读它决定写 paused 还是 cancelled。
- `controlMu`:独立于 `p.mu`,避免与 handler 注册/回调锁互相阻塞。

### 4.2 executeTask 改造(收尾拦截)

```
executeTask(task):
  ...
  execCtx, taskCancel = context.WithCancel(p.ctx)      // 每个任务独立可取消 ctx
  runningCancels[task.ID] = taskCancel                 // 注册
  defer: 注销 + taskCancel()                           // 必清理,防泄漏

  if task.Timeout > 0:
      execCtx, timeoutCancel = context.WithTimeout(execCtx, task.Timeout)
      defer timeoutCancel()

  result, execErr = handler(execCtx, task)             // 业务执行

  // ===== 干预检查:必须在 retry/completed/failed 分支之前 =====
  desired, intervened = stopSignals[task.ID]
  if intervened:
      delete(stopSignals, task.ID)
      if desired == StatusPaused:
          // 强制落库最新进度(从 progress 缓存读),再写 paused
          UpdateStatus(id, StatusPaused, "")
      else:
          UpdateStatus(id, StatusCancelled, "任务已终止")
      checkBatchCompletion(task)
      return

  // ===== 原有分支逻辑不变 =====
  // (retry / failed / completed)
```

**顺序是硬性要求**:干预检查必须在 retry 分支之前。否则 handler 因 cancel 返回 `context.Canceled`,会被当成普通失败触发重试——"停止"变成"重跑"。

### 4.3 Stop/Terminate 的竞态防护

```go
func (p *TaskPool) Stop(id string) error {
    p.controlMu.Lock()
    cancel, ok := p.runningCancels[id]
    if ok {
        p.stopSignals[id] = StatusPaused   // ① 先记意图(锁内)
        p.controlMu.Unlock()
        cancel()                            // ② 再发信号(锁外)
        return nil
    }
    p.controlMu.Unlock()
    return ErrTaskNotRunning
}
```

**先记意图、再发信号,顺序不可反**。cancel 调用后 handler 可能立刻退出并进入收尾,如果 stopSignals 还没写入,收尾读不到信号,任务会被当成正常失败处理。

Terminate 与 Stop 同构,终态为 `StatusCancelled`。

### 4.4 Start 的入队去重

```go
func (p *TaskPool) Start(id string) error {
    task, err := p.backend.Get(id)
    switch task.Status {
    case StatusDelayed, StatusPaused, StatusFailed, StatusCancelled:
    default:
        return ErrTaskNotStartable
    }
    if task.Status != StatusPaused {
        task.Retries = 0 // 重新运行视为全新
    }
    task.Status = StatusPending
    task.ScheduledAt = time.Time{} // 延迟任务立即执行
    task.StartedAt, task.DoneAt, task.Error = nil, nil, ""
    return p.backend.Enqueue(task)
}
```

- **SQLite/MySQL**:`Enqueue` 已实现"存在则 UPDATE"(原 v0.3.x 逻辑),本次把 UPDATE 扩展为**完整同步调度字段**(status/priority/scheduled_at/started_at/done_at/error/retries),保证重新激活时清理历史执行痕迹。
- **Memory**:`Enqueue` 原实现无条件 push 堆,Start 连续调用两次会在堆里出现同一任务两份。本次新增 `inQueue map[string]bool` 跟踪堆内 id,**已入队则跳过**(但同步任务状态 + 唤醒 Dequeue,否则延迟任务提前执行时 worker 无人唤醒)。

### 4.5 回调与指标

- 干预终态(**paused/cancelled**)不触发 `OnComplete`/`OnFailed`,但**仍触发 `checkBatchCompletion`**(批次计数不泄漏)。
- `OnStart` 在注册 cancel 之前调用(不受影响)。
- 指标(`Metrics`):干预路径不增加 completed/failed 计数;`running` 计数由 executeTask 的 defer 正常递减。
- `OnProgress` 回调不受影响;Stop 时从 `p.progress` 缓存读最新进度强制落库,保证 Continue 后续跑进度不丢。

### 4.6 Recover 兼容

现有 `Recover()` 把 `status=2`(running)重置为 pending,是**崩溃恢复**语义。`StatusPaused=7` 不在重置范围内,**手动暂停的任务重启后不会自动跑**——符合预期(用户主动暂停 ≠ 崩溃遗留)。SQL 无需改动。

### 4.7 已知边界(诚实说明)

| 场景 | 行为 | 说明 |
|---|---|---|
| handler 不响应 ctx.Done() | 任务继续跑完,但终态仍记为 paused/cancelled,Result 不落库 | 协作式固有边界;框架语义正确,停止时间不可控 |
| Remove 运行中任务 | 返回 ErrTaskNotRemovable,拒绝删除 | 用户明确要求"只能等任务停止后移除" |
| StopTask 的异步性 | cancel 返回 ≠ 任务已暂停,需轮询 `GetTask(id)` 看状态 | 前端要"点了停止→轮询到 paused" |
| 并发 StopTask 同一任务 | 多次调用安全,`runningCancels` 删除后第二次返回 ErrTaskNotRunning | 幂等性由调用方决定 |
| memory 后端并发安全 | `Save`/`Enqueue`/`Get`/`List*`/`Dequeue` 全部返回或存储**副本**,map 内对象只在锁内修改 | 修复了 v0.3.x 遗留的 task 指针共享竞态(race detector 验证) |

### 4.8 排空语义(停止/终止的核心)

用户需求:

> 停止:小任务如果在执行就继续执行完成,但不能有新的任务执行了,已经进入执行的小任务执行完成就停止任务。

实现方式(框架 + 业务约定):

```go
// 框架侧(cancel 信号)已经就绪。
// 业务侧(handler)的关键约定:ctx 检查点必须放在"小任务之间":
for i, item := range items {
    select {
    case <-ctx.Done():
        return nil, ctx.Err()  // 当前小任务已完成,不再启动下一个
    default:
    }
    doWork(item)  // 正在执行的小任务不会被中途打断
}
```

- 正在执行的小任务:**不会被中途打断**(只要 doWork 内部不检查 ctx)
- 停止信号到达后:**不再启动新的小任务**(循环顶部检查)
- 排空完成后 handler 返回 → executeTask 收尾写 paused/cancelled
- 框架不需要为此改任何代码——ctx 协作式机制天然支持,验证见 `TestStopDrainFinishesCurrentItem`

## 8. 对闲鱼(pooladapter)的迁移指引

### 8.1 必须做的检查

闲鱼 handler 已经用了"进度回调 + ctx 中断"的写法(7月28日重构),但**不是每个循环点都检查了 ctx**。v0.4.0 上线后:

- 批量核价/发布等长循环 handler,确认每个迭代都有 `ctx.Err()` 检查(或 `select { case <-ctx.Done(): ... }`)
- 没有检查的地方补上,否则 Stop 按钮"点了没反应"

### 8.2 前端接入建议

```
任务列表(每个任务):
├── 运行中 → [停止] [终止] [移除置灰]
├── 已暂停 → [继续] [终止] [移除]
├── 延迟中 → [立即执行] [终止] [移除]
├── 失败/已取消 → [重新启动] [移除]
└── 已完成 → [移除]

交互规范:
- 点"停止/终止"后,按钮置灰,轮询 GetTask 直到状态变为 paused/cancelled(排空是异步的)
- 点"移除"时若返回 ErrTaskNotRemovable,提示"任务正在运行,请先停止"
- 所有按钮失败(返回 error)时 toast 展示错误
```

### 8.3 不要做的

- 不要用 `Pause()`/`Resume()`(池级空壳,会误导)
- 不要依赖"Stop 立即生效"(协作式,等 handler 响应)

## 9. 后续演进(非本次范围)

- **StopWait/StopTimeout**:Stop 后最多等 N 秒,超时返回"仍在运行",给前端确定性反馈
- **池级暂停**:全局 `Pause()`/`Resume()` 落地(需要在 workerLoop 加闸门)
- **任务的资源限制**:单任务 CPU/内存上限(需进程隔离,大改造)
- **恢复点 checkpoint**:paused 任务在 metadata 里写 checkpoint,Continue 时从断点续跑(闲鱼 `runPricingLoop` 已有雏形)
